# Fluxy Wire Protocol v1

Status: draft for M0. This document is the implementation contract for
`fluxy-proto`; `docs/DESIGN.md` remains the product design.

## 1. Transport

- QUIC with TLS 1.3 and mutual certificate authentication.
- ALPN: `fluxy/1`.
- One bidirectional control stream per session. Each file transfer uses one
  more bidirectional stream, opened by the receiver and named with its
  `transfer_id` (section 8.2).
- Scheduling: both peers set priority 100 on the session control stream, so
  chat, clipboard, and negotiation frames are never queued behind bulk payload
  (a saturated 10 GiB transfer must not delay chat by more than the M2-09
  budget). Chunk payload rides the transfer stream, which keeps the default
  priority.
- No plaintext listener, no cloud relay, and no certificate-verification bypass.

## 2. Control frame

Every control message is:

~~~text
+----------------------+---------------------------+
| length: u32 (BE)     | protobuf Envelope (length)|
+----------------------+---------------------------+
~~~

- `length` is the Envelope byte count, not including the prefix.
- Maximum Envelope size: **8 MiB** (8,388,608 bytes).
- A decoder must reject a declared length above the limit before allocating.
- A decoder must reject `length != actual_body_len`.

## 3. Envelope

```proto
message Envelope {
  uint32 protocol_version = 1;
  bytes message_id = 2;       // 16 bytes, UUIDv7
  bytes source_device_id = 3; // 16 bytes
  bytes session_id = 4;       // 16 bytes, zero in Hello/HelloAck
  int64 created_at_ms = 5;
  int32 kind = 6;
  bytes payload = 7;
}
```

Validation before encode or after decode:

1. `protocol_version == 1`.
2. `message_id` is 16 bytes and has the UUIDv7 version nibble.
3. `source_device_id` is 16 bytes and is not all zero.
4. `session_id` is 16 bytes; it is all zero for Hello/HelloAck.
5. `kind` maps to a known `MessageKind`; unknown values are rejected.
6. Envelope size is at most 8 MiB.

Identifiers are opaque 16-byte values on the wire. JSON representations use
canonical UUID strings. `created_at_ms` is Unix milliseconds and is advisory;
receivers must not use it for ordering.

## 5. Handshake

All messages except HELLO/HELLO_ACK carry a non-zero `session_id` generated by
the initiator after HELLO_ACK. HELLO and HELLO_ACK carry an all-zero session id.

1. Initiator opens QUIC with a self-signed certificate and sends HELLO with a
   random 32-byte nonce, its certificate fingerprint, its Ed25519 public key,
   and a signature over the Hello transcript.
2. Responder verifies that the Hello certificate fingerprint matches the TLS
   client certificate, verifies the Hello signature, then replies HELLO_ACK
   with the same fields and its own nonce and signature.
3. Initiator pins the server certificate by BLAKE3 fingerprint, verifies the
   HelloAck signature, and generates a UUIDv7 `session_id`.
4. Both sides exchange CAPABILITIES. Values are intersected, unknown features
   are ignored, and the initiator's session id is echoed.
5. Both derive the same 6-digit SAS from sorted
   `(device_id, nonce, cert_fingerprint)`.
6. Both devices display the SAS and wait for an explicit local decision; the
   desktop prompt can wait up to **120 seconds** and never auto-confirms. The
   initiator sends PAIR_REQUEST with the SAS; the responder checks it, sends
   PAIR_REPLY, and the initiator sends PAIR_CONFIRM. READY completes the
   exchange.
7. Both sides persist the peer public key and certificate fingerprint only
   after the SAS is accepted. A mismatch, rejection, cancellation, or timeout
   writes no trust state.
8. The responder throttles repeated failed pairing attempts per source IP:
   five failures start a cooldown that doubles from 2s and caps at 60s.

### Trusted resume

`Hello` and `HelloAck` carry a signed `resuming` flag (field 9). It is part of
the transcript hash, so a peer cannot change it without invalidating the
signature. A reconnect uses the same handshake but sets `resuming = true`:

1. The initiator loads the server entry from its trust store and pins the server
   certificate as usual. It must already have a trust entry for that device; an
   unknown server is never resumed.
2. The responder requires a trust entry for the claimed device id. It compares
   the stored Ed25519 public key and the **actual TLS client certificate**
   fingerprint (not the fingerprint merely claimed in Hello) with the entry.
3. The responder replies with `HelloAck.resuming = true` and both sides still
   exchange `CAPABILITIES` and `READY`.
4. `PAIR_REQUEST`, `PAIR_REPLY`, `PAIR_CONFIRM`, and the SAS prompt are
   skipped. No trust entry is written or refreshed.
5. A missing entry, changed key, changed certificate, or mismatched resume flag
   fails the handshake with an `ERROR` using the stable `Trust` code
   (`1004`). The responder writes no trust state.

The server accepts a bootstrap client certificate only for the first pairing.
On every resume it enforces the stored client pin, and the client enforces the
pinned server certificate.

mDNS/DNS-SD records are hints only. They are never used as identity proof.

## 6. Capabilities

`CAPABILITIES` carries:

| Field | Meaning |
| --- | --- |
| `max_control_frame` | Sender's encoded Envelope limit |
| `max_chunk_size` | Largest accepted chunk payload |
| `max_streams` | Concurrent transfer stream limit |
| `features` | `folder`, `resume`, `clipboard` |
| `clipboard_max_bytes` | Largest accepted clipboard payload |

Each side uses the intersection. Missing/unknown features are disabled rather
than assumed.

## 7. Control session and chat

After `READY`, the initiator opens one bidirectional stream for control
messages. The responder accepts it. File chunks never share this stream: every
transfer opens its own bidirectional stream and names it (section 8.2).

- Framing is the same length-prefixed Envelope as section 2.
- The stream carries `PING`, `PONG`, `CHAT_TEXT`, `MESSAGE_ACK`, `ERROR`, and
  later clipboard/transfer control messages.
- Each side sends `PING` every **10 seconds**. A valid inbound control frame
  refreshes the receive timestamp. If no valid frame (including `PONG`) arrives
  for **30 seconds**, the peer is treated as half-open, the stream is closed,
  and a disconnect is reported.
- `CHAT_TEXT` carries UTF-8 in `text` (maximum **32 KiB**), an optional
  `copy_hint`, and a per-session `sequence` starting at 1. Chat is held in
  memory only and is never written to disk.
- The receiver acknowledges each accepted `CHAT_TEXT` with `MESSAGE_ACK`
  referencing the `CHAT_TEXT` Envelope `message_id` and `delivered = true`.
  The acknowledgement means the message was accepted into the in-memory inbox,
  not that a UI painted it. Duplicate message ids within the recent-window
  (1024 ids) are acknowledged but not delivered twice.
- The sender may reuse the same `message_id` when retrying an unacknowledged
  message; the receiver's duplicate window makes that safe within a session.
  The persistent client keeps the recent-id window across reconnects, so a
  retry after reconnect is acknowledged but not delivered twice.
- The desktop chat runtime opens a trusted resume for the selected peer and
  accepts a trusted inbound resume as a chat session. A chat session is
  independent of pairing: SAS is never repeated for an already-trusted peer.
- If the control stream ends before a `MESSAGE_ACK`, the desktop runtime keeps
  the message in a failed, retryable state. Manual retry sends the original
  `message_id` again; it does not generate a new id, so the receiver can
  suppress a duplicate. The transport never replays failed messages on its own.
- The desktop transcript is bounded to 1000 messages and is memory-only. It is
  cleared on app exit and on identity rotation; peers' text is rendered as
  text, never HTML.
- A broken control stream is recoverable. The client reconnects to the same
  server device id with a trusted resume, never repeating the SAS. Retry
  delays use base values of **1, 2, 4, 8, 15, 30 seconds**, then 30 seconds,
  with up to 20% jitter and a hard 30-second cap. A successful reconnect creates
  a new session id and control stream; unacknowledged chat is not replayed
  automatically by the transport.

### 7.1 Clipboard text

Clipboard sharing is a three-step, receiver-authorized exchange. The sender
never writes the receiver's clipboard and the receiver never accepts text just
because it arrived.

1. `CLIPBOARD_OFFER` (kind 30) carries `size_bytes`, a BLAKE3 `digest`, a
   bounded `preview`, a per-session `sequence`, `ttl_ms` (the desktop clamps it
   to 5000 to 600000; it uses 120000), the UUID of the device that first copied
   the text (`origin_id`), and `hop` (0 for a local share). The Envelope
   `message_id` is the offer id. The offer contains no body text beyond the
   preview. A pending offer is kept in memory only. Receivers reject `hop > 1`;
   this version never forwards an offer to a third device.
2. The receiver consults its persisted per-device policy. **Ask** is the
   default and shows the peer, preview, and size until the user explicitly
   accepts or rejects. **Auto** is only available after the user explicitly
   authorizes that trusted device and accepts without a per-offer prompt.
   **Reject** declines without prompting. Accepting sends `CLIPBOARD_ACK`
   (kind 32) with `accepted = true` and `applied = false`; rejecting sends
   `accepted = false` with a stable code. A receiver that has no consent UI
   (for example headless `fluxy-cli serve`) rejects with `cli_no_consent`.
3. Only after an accepted ACK does the sender send `CLIPBOARD_TEXT` (kind 31)
   with the same `offer_id`, the UTF-8 `text`, and its BLAKE3 `digest`. Text is
   at most 1 MiB. The receiver checks the offer id, pending state, expiry, size,
   and digest before writing the OS clipboard. A failed write or digest
   mismatch produces `CLIPBOARD_ACK { accepted: true, applied: false, code }`;
   success produces `applied = true`.

- Offers are not retried automatically and expire without user action.
- The receiver sends at most one ACCEPT and one final ACK per offer. The sender
  must not send text twice for the same offer.
- Clipboard text is memory-only on both sides. It is not written to the
  transcript, disk, or logs; only the bounded preview and status may be shown.
- Automatic clipboard sharing (background read/send) remains off by default
  and is a desktop auto-sync feature, not part of the M1 clipboard flow. Each
  device has its own receive policy; auto-receive is never the default.
- The receiver keeps the last 16 applied BLAKE3 digests for five minutes. An
  offer whose digest is still present is declined with `duplicate_content`
  before it can be written again; locally received content is also refused at
  send time with `clipboard_duplicate`. This suppresses echoes and A→B→A
  loops, including when a forwarder is involved.
- An offer whose `origin_id` equals the local device id is declined with
  `echo_suppressed`. Unknown, expired, already-consumed, or wrong-peer offers
  are ignored or rejected with a stable code.

## 8. Binary chunk header

File chunks do not use protobuf:

~~~text
offset  size  field
0       4     magic "FCH1"
4       16    transfer_id
20      4     chunk_index (u32 BE)
24      8     offset (u64 BE)
32      4     payload_len (u32 BE)
36      32    BLAKE3(payload)
68      N     payload
~~~

- Chunk payload is at most 4 MiB in v1.
- `payload_len` must match the remaining bytes.
- `offset + payload_len` must stay within the declared file size.
- The receiver verifies BLAKE3 before acknowledging durable storage.
- `FileHandleId` and platform paths are local-only and never appear in a chunk
  or control frame; M2-01 keeps the mapping inside the local file manager.

### 8.1 Manifest

`TRANSFER_MANIFEST` carries the per-file manifest as an ordered list of 32-byte
block hashes plus two derived values:

- `block_size` is 4 MiB by default and is capped at 64 MiB.
- `file_size` is the exact byte length; the last block may be shorter.
- `root_hash` = BLAKE3 of the whole file byte stream.
- `manifest_digest` = BLAKE3 of the block hashes concatenated in index order.
- A manifest is limited to 32768 blocks (about 4 MiB), so a 128 GiB file at the
  default block size still fits the control-frame cap.

M2-02 computes the manifest locally with a parallel window pass and caches it
against the source identity. M2-03 sends it and uses the block hashes for chunk
verification; M2-06 adds the root-hash check after the last block.

### 8.2 Pull window and retries

The receiver drives the transfer; the sender never pushes an unrequested chunk.

- The receiver opens one bidirectional stream per file and writes the 16 raw
  bytes of `transfer_id` before anything else. One stream carries the whole
  file: the name, the manifest, every request and acknowledgement, and every
  chunk.
- QUIC does not say which transfer opened an accepted stream. The sender reads
  the name and serves the transfer it identifies, so two transfers in flight on
  one connection never swap streams. A stream named for a transfer the sender
  has not registered yet is parked until it registers, never reset: it is the
  receiver's only stream for that file.
- `TRANSFER_MANIFEST` (`TransferManifest`) carries `transfer_id`,
  `block_size`, `file_size`, the ordered `block_hashes`, `root_hash`, and
  `manifest_digest`. It is the sender's first frame on the transfer stream. The
  receiver sends its first request batch, then validates every hash length, the
  block count, `manifest_digest`, and the transfer id before writing a chunk.
- `CHUNK_REQUEST` (`ChunkRequest`) names one `transfer_id` and
  `chunk_index`; `CHUNK_ACK` (`ChunkAck`) echoes both plus `stored` and a
  stable `code`.
- The default window is 16 outstanding chunks (8 × 2). A request that is not
  acknowledged within 15 s is retried; after 3 attempts the chunk is reported
  missing and the transfer fails instead of hanging.
- Control frames and chunk frames share the stream and are told apart by their
  first four bytes: a control frame is a 4-byte length followed by an Envelope
  (section 2), a chunk starts with `FCH1`. The magic is far above the 8 MiB
  frame cap, so the two can never be confused.
- A chunk is read as its fixed 68-byte header followed by `payload_len` bytes
  (section 8). Neither side reads to end of stream: the stream stays open for
  the whole transfer.
- The receiver hash-checks a chunk against the header and the manifest block
  hash before writing it to the sink, then acknowledges it. Duplicate chunks
  (a timed-out request served twice) are written at most once and counted once.
- `offset` must equal `chunk_index * block_size`, and `payload_len` must equal
  the manifest block length; a mismatch is rejected without writing.

M2-03 implements this scheduler and the two frames; M2-04 persists the bitmap as
a resume checkpoint, and M2-06 adds the `root_hash` check after the last block.

### 8.3 Resume checkpoints

A transfer survives a restart through a per-transfer checkpoint directory:

~~~text
<app-data>/checkpoints/<transfer-id>/manifest.bin
<app-data>/checkpoints/<transfer-id>/progress.bin
~~~

- `manifest.bin` is the `FMF1` frame: magic, format version, block size, file
  size, root hash, manifest digest, block count, and the ordered 32-byte block
  hashes. Loading validates the magic, version, block-size cap, block count,
  exact length, and that `manifest_digest` matches the hashes.
- `progress.bin` is `FCP1 | version | payload length | JSON | BLAKE3(JSON)`.
  The JSON carries `schema`, `transfer_id`, `role` (sender or receiver),
  `file_name`, `state`, the sender’s source identity (size and modification
  time), `updated_unix_ms`, and the received-block bitmap. A torn, truncated,
  or checksum-mismatched file is rejected instead of resumed.
- Both files are written by flushing and fsyncing a temporary sibling, removing
  the previous entry, and renaming the temporary into place, so a crash never
  exposes a half-written checkpoint.
- The receiver persists after every `interval` received chunks (one by default)
  and marks the state `interrupted` or `completed` when the pull ends. The
  sender records its source identity so a restart can compare it with the live
  file before serving again.
- Resume requires the stored manifest digest, block size, and file size to match
  the manifest offered for the new attempt. A mismatch, a corrupt progress file,
  or a bitmap whose length differs from the manifest block count discards the
  checkpoint and restarts the transfer; two different content versions are never
  stitched together.
- On resume the receiver sends `CHUNK_REQUEST` only for missing blocks; the
  `TRANSFER_RESUME` kind notifies the peer about the state change (M2-07).

M2-04 implements this store and the resumable pull; M2-05 adds pause, cancel,
and retry over the same states, and M2-06 verifies `root_hash` before the
partial file is renamed into place.

### 8.4 Pause, cancel, and retry

The transfer loops poll a local `TransferControl` handle on every tick, so a
pause or cancel is observed within one `TRANSFER_TICK` (100 ms):

- **Pause** stops the receiver from issuing new requests and requeues the
  outstanding window. A pause is not a failure: it never consumes the retry
  budget, and chunks already in flight are still accepted and written. The
  checkpoint moves to `paused` and keeps the partial file, so resume re-issues
  only the missing blocks from the bitmap.
- **Cancel** wins over a pause and is idempotent. The pull returns 3008
  `Canceled`, the state machine moves to `cancelled`, the partial file is
  discarded, and the checkpoint is removed unless the caller opts to keep it
  (`keep_checkpoint_on_cancel`). A cancelled transfer leaves no temporary file.
- **Retry** is a user-triggered transition back to `transferring` from
  `failed`, `interrupted`, `paused`, or `cancelled`. Retrying an interrupted or
  paused transfer continues from its checkpoint; retrying a cancelled transfer
  starts from a fresh sink.
- Illegal transitions are rejected with `StateError` (3001) instead of being
  written: only the core may move a transfer, and a completed transfer is
  terminal.

M2-05 pauses and cancels the local side, and a cancel simply closes the control
stream so the peer stops. M2-07 adds the transfer center, which also sends
`TRANSFER_PAUSE`, `TRANSFER_RESUME`, and `TRANSFER_CANCEL` so the peer learns
about the state change before the stream closes (see section 8.6).

### 8.5 Integrity, finalize, and source change

Verification happens on both ends and in two stages, so a peer can never hand
the user a file whose bytes do not match the manifest:

- **Per block.** Every chunk frame carries the BLAKE3 hash of its payload
  (`FCH1` header). The receiver rejects a frame whose payload hash or manifest
  hash does not match, names the block from the header, and re-requests it on
  the next tick without writing the tampered bytes. A rejected block still
  counts toward its retry budget; when the budget is exhausted the transfer
  fails with 3006 `MissingChunks`. A frame whose header cannot be parsed is a
  protocol violation and fails the transfer immediately.
- **Whole file.** After the last block is written and the sink is flushed, the
  receiver hashes the partial file with BLAKE3 in 1 MiB blocks and compares the
  result with `manifest.root_hash`. Only a match may move the state
  `verifying -> completed`; a mismatch fails the transfer with 3005
  `HashMismatch`, drops the checkpoint, and discards the partial file. The root
  hash also covers the empty-file case.

Finalize is the only step that makes a file visible: the sink renames
`.fluxy-<transfer-id>.part` over the destination only when every byte is covered
and the root hash matched. Until then the transfer owns a hidden temporary
file, so an interrupted or failed transfer never exposes a partial file under
the user-visible name.

**Source change (3002).** The sender re-stats the source before serving each
request and compares the result with the identity captured when the file was
opened (size and modification time). A change returns 3002 `SourceChanged` and
closes the transfer instead of serving mixed content; a read that hits EOF
below the recorded size reports the same code.

M2-06 implements this stage and M2-07 surfaces 3005/3002 in the transfer center
with the code, the numeric code, and the retryable flag; M2-09 drives the
sender-side check with a real mid-transfer file change.

### 8.6 Negotiation, progress, and the transfer center

M2-07 adds the application-layer handshake that drives a transfer from the
transfer center:

- **Offer.** The sender hashes the file (through the cached manifest) and sends
  `TRANSFER_OFFER` on the control stream with `transfer_id`, `file_name`,
  `file_size`, `block_size`, `root_hash`, `manifest_digest`, `total_files`,
  `total_bytes`, and an optional inline manifest. The receiver validates the
  manifest summary, refuses a file name that escapes the receive root, records
  the offer as `offered`, and raises the incoming-offer prompt. Nothing is
  written before the user answers, and a repeated `transfer_id` reuses the
  existing record instead of creating a second one.
- **Accept and reject.** `TRANSFER_ACCEPT` starts the pull. `TRANSFER_REJECT`
  carries a `code` and `message` and fails the sender side with that code. A
  receiver that never answers times out after 60 s and fails the sender with
  4201 `peer_offline` semantics at the application layer.
- **Progress.** While a receiver writes durable blocks it reports
  `TRANSFER_PROGRESS{bytes_done, bytes_total}` and raises a local UI event.
  Both are throttled to at most one emission per 100 ms per transfer; terminal
  events (`TRANSFER_COMPLETE`, `TRANSFER_ERROR`) are never throttled. Progress
  is advisory: the receiver still derives its requests from its own bitmap, so a
  dropped or forged progress frame cannot change what is written.
- **Pause, resume, cancel, and retry.** The transfer center maps those actions
  onto the local `TransferControl` handle and also sends `TRANSFER_PAUSE`,
  `TRANSFER_RESUME`, or `TRANSFER_CANCEL` so the peer learns about the state
  change. A cancel still closes the transfer stream, which stops a peer that
  never saw the frame.
- **Errors.** `TRANSFER_ERROR{code, message, retryable}` mirrors
  `TransferError::code()` and `is_retryable()`; the UI keeps the code, the
  numeric code, and the retryable flag, and only offers retry when a retry can
  plausibly succeed (transport, control, timeout, 3005, and 3006, but not a
  3002 source change).
- **No paths on the wire.** Control frames carry only `transfer_id`, metadata,
  and hashes; a local path or file handle never appears in a frame. On the
  desktop the native file picker runs in Rust and returns an opaque
  `{file_id, name, size}` handle, so the WebView never sees a filesystem path.

### 8.7 Batch queue and the active-transfer cap

M2-08 adds the batch entry points and a global concurrency cap:

- **Drag and drop.** The window drop handler runs in Rust, so the WebView never
  receives a local path: a drop registers every file and publishes the batch as
  opaque handles plus base names, and the transfer center opens the send
  confirmation with it. Directories are refused until the folder batch lands in
  M3-07.
- **Batch.** A send is a list of registered handles; each file becomes its own
  `transfer_id` with its own manifest and checkpoint, so one failure never
  blocks the rest of the batch. At most 100 files may be queued per send (plan
  section 5.8); a larger or empty batch is rejected before any transfer exists.
- **Queue.** The number of simultaneous active transfers is capped (default 2,
  configurable from the transfer center). A send that cannot start is recorded
  as `queued` and promoted to `preparing` when a slot frees, in creation
  order. A paused transfer keeps its slot, a terminal transition hands its slot
  to the next queued send, and a retry re-enters the queue instead of bypassing
  the cap.
- **Inbound admission.** An incoming offer is admitted only while the device is
  below its cap, counting the offers that were admitted but not answered yet.
  Otherwise the receiver answers `TRANSFER_REJECT` with code `peer_busy`
  (2002) and the sender fails that transfer with the same code. An offer that
  was already admitted always starts when the user accepts it, so the peer is
  never left waiting behind a local queue. An admitted offer that nobody
  answers expires after 60 s — the same patience the sender has — and releases
  its slot to the next queued send.


## 9. Discovery

### 9.1 mDNS/DNS-SD

- Service type: `_fluxy._udp.local.`; instance name is the device UUID.
- SRV host is `<device-uuid>.local.` and the SRV port is the QUIC listener.
- A/AAAA records contain the addresses of the selected interface only. Loopback
  and other interfaces are never advertised unless an explicit dev flag allows
  loopback.
- TXT keys:
  - `id`: canonical UUID string; stable across address changes.
  - `name`: display name, at most 128 characters.
  - `os`: platform label, at most 64 characters.
  - `v`: decimal protocol version; peers with a different version are ignored.
  - `features`: comma-separated capability hints, for example `chat`.
  - `fp`: 64 lowercase hex characters containing the BLAKE3 fingerprint of the
    advertised TLS certificate. It is a pin hint only, never authentication
    evidence; a peer without a valid 32-byte `fp` is ignored.
- Browser filters malformed TXT, nil IDs, zero ports, empty address sets, its
  own device ID, incompatible versions, and missing/invalid `fp`. It does not
  fail the browse.
- The peer table is keyed by stable device ID, so an address or port change
  updates one record instead of creating a second device. A resolved record
  stays online for **120 seconds** without a refresh; a service removal or TTL
  expiry transitions it offline. mDNS is a hint, so a stale record can only lead
  to a failed connection or a new SAS prompt; it never grants trust.
- When an interface is selected, the daemon disables all other interfaces before
  enabling the selected name. This applies to both advertise and browse sockets.
- A record, address, and TXT field are hints. They never establish identity and
  never bypass the TLS handshake or SAS confirmation.

### 9.2 Hotspot gateway fallback

- Client sends `FLUX-DISCOVER/1` + 16-byte device id + 32-byte nonce to the
  default gateway on UDP **42420**, then limited broadcast.
- A probe is only a hint; it never creates trust or bypasses the handshake.
- Planned for M1-10; the wire probe codec is already present.

## 10. Compatibility rules

- Add fields with new numbers; never renumber or reuse.
- Unknown Envelope fields are ignored by protobuf, but unknown `kind` values
  are rejected.
- A peer that cannot agree on protocol version or mandatory capabilities is
  rejected with a stable error code.
- Stable error codes are defined in `fluxy-core::error`.

## 11. Test vectors

The M0-01 tests cover round-trip, truncated frames, declared/actual length
